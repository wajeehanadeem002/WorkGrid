# WorkGrid System Design

## Scope

WorkGrid is a multi-tenant project-management SaaS. Organizations are the tenant boundary. The application includes organization membership and invitations, projects, tasks, comments, private attachments, dashboards, audit history, account and organization settings, server-side search/filtering/pagination, and JSON/CSV export.

The application is prepared for Vercel, Clerk, and Supabase, but this repository task does not create or mutate external resources and does not deploy.

## Architecture

WorkGrid is a modular Next.js App Router application. React Server Components render authenticated reads. Server Actions own form mutations. Route Handlers own downloads and exports. Domain modules keep validation, permissions, database access, and presentation separate.

Clerk is the sole identity provider. Supabase trusts Clerk session JWTs through its native third-party authentication integration. The Clerk subject is stored as a text `user_id`; WorkGrid does not duplicate profiles or credentials.

Supabase Row Level Security is a second, independent authorization boundary. The application always checks authentication, membership, role, and resource ownership before data access, while RLS applies the same tenant constraints in PostgreSQL. Normal application traffic uses the publishable Supabase key with the Clerk token. A service-role key is not used by normal actions or queries.

## Application boundaries

- `src/app`: routes, layouts, loading/error/not-found states, Server Actions, and Route Handlers.
- `src/features`: organization, project, task, member, comment, attachment, dashboard, audit, and account components and domain schemas.
- `src/lib/auth`: authenticated actor resolution and authorization guards.
- `src/lib/data`: typed Supabase queries and mutations.
- `src/lib/supabase`: authenticated server-client construction and database types.
- `src/lib/security`: error mapping, rate limiting, upload policy, and security helpers.
- `src/lib/ui`: URL state, pagination, dates, and display utilities.
- `supabase/migrations`: schema, indexes, triggers, functions, RLS, and Storage policies.
- `supabase/tests`: pgTAP coverage for constraints, roles, tenant isolation, and Storage isolation.

## Tenant and authorization model

Every tenant-owned row contains `organization_id`. Composite foreign keys enforce that a task belongs to a project in the same organization, a comment belongs to a task in the same organization, and an attachment target belongs to the same organization.

Roles are ordered `member < admin < owner`. Owners administer settings and all members. Admins manage projects, tasks, invitations, and non-owner members but cannot promote anyone to owner, modify an owner, remove an owner, or transfer ownership. Members can read organization work, create and update tasks, assign members, comment, and upload permitted attachments. Project creation and destructive administration require admin or owner.

An owner cannot be removed or demoted. Ownership transfer is intentionally not implemented. An organization always has at least one owner.

All server entry points use the following sequence:

1. Resolve and require the Clerk subject.
2. Parse and validate untrusted input.
3. Resolve the organization through membership, never from trust in a submitted ID.
4. Enforce the required role.
5. Resolve nested resources using both their identifier and organization identifier.
6. Perform the operation through a Clerk-authenticated Supabase client.
7. Return a sanitized result and invalidate only tenant-specific paths.

## Data model

Core tables are `organizations`, `organization_members`, `organization_invitations`, `projects`, `tasks`, `comments`, `attachments`, `audit_logs`, and `rate_limit_windows`.

UUID primary keys are generated by PostgreSQL. User references are Clerk subject strings. Slugs and project keys are case-insensitively unique within their scopes. Timestamps use `timestamptz`. Controlled status and role fields use PostgreSQL enums. Check constraints reject blank names, invalid attachment metadata, invalid invitation lifetimes, and invalid task dates. Composite unique constraints support tenant-safe foreign keys.

Audit rows are append-only. Database triggers capture organization, membership, project, task, comment, and attachment mutations with the authenticated actor and a deliberately small metadata payload. Direct update and delete are blocked, including through normal authenticated policies.

## Storage

The `attachments` bucket is private. Object paths follow `organization-id/project-id/task-or-project/random-id/sanitized-name`. The upload allowlist contains PDF, plain text, CSV, PNG, JPEG, GIF, and WebP. Each file is limited to 4 MiB so multipart requests remain below Vercel's Function payload ceiling. Executable and ambiguous MIME types are rejected before upload.

Uploads use a reserve-upload-seal-verify-finalize flow: authorize and reserve metadata, upload to the private bucket, bind the exact object into an immutable verification state, re-download and hash the stored bytes, and only then promote the row to ready with a separate server proof. Failed verification enters a non-readable discard state until object and metadata cleanup completes. Trusted deletion records a reversible deleting state before object removal and reconciles metadata from the actual Storage result. A documented cleanup process handles stale reservations, verification/discard states, and orphaned objects. Downloads stream through an authenticated, tenant-authorized application route so reusable Storage URLs are not exposed.

## Rate limiting

Private PostgreSQL logic maintains fixed-window counters keyed by a one-way hash of actor and a database-approved scope. Authenticated clients receive only bounded, operation-specific entry points; they cannot choose keys, limits, windows, or operation names. Conservative limits cover organization and invitation operations, comments, uploads, and exports. Rate-limit records contain no raw credential and expire through a documented scheduled cleanup query.

## User experience

The public surface includes a restrained landing page and Clerk sign-in/sign-up routes. Authenticated routes use an organization-scoped workspace with sidebar navigation, a compact mobile header, breadcrumbs, search/filter forms, accessible tables/cards, confirmation dialogs, and server-rendered loading, empty, error, and success states.

The visual system uses neutral slate surfaces, an indigo accent, strong hierarchy, subtle borders, consistent spacing, visible focus rings, and high-contrast status treatments. The interface uses no decorative imagery. Tables adapt into stacked cards on narrow screens.

## Errors and testing

Expected failures use typed public error codes: validation, unauthenticated, forbidden, not found, conflict, rate limited, and unavailable. UI messages never expose SQL text, secrets, stack traces, or provider payloads. Unexpected failures are logged server-side with a request correlation identifier and return a generic message.

Vitest covers validation, role rules, pagination, upload policy, rate-limit decisions, error mapping, and data-access orchestration. React Testing Library covers forms, filters, permission-based controls, and empty/error states. Integration-boundary tests use injected authenticated clients to verify organization scoping and denial behavior. pgTAP tests run against local Supabase to prove RLS, cross-tenant denial, role restrictions, composite relationships, append-only audit rows, and private Storage isolation.

CI installs from the lockfile, checks formatting, linting, types, unit/component tests, and the production build. A database job runs Supabase migrations and pgTAP tests in GitHub Actions.

## Performance and caching

Reads are server-side and paginated. Search uses indexed normalized text and trigram support where useful. Aggregate dashboard queries are grouped rather than issued per project. Tenant data is dynamic and is never placed in shared public caches. Mutations invalidate only organization-scoped paths.

## Delivery constraints

No commit, push, merge, deployment, screenshot, or repository QA artifact is part of this implementation session. The complete working tree remains available for review.
